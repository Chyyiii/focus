# FOCUS 2.0: план реорганизации и перехода на собственную инфраструктуру

Статус: предложение для утверждения Founder. Исходит из BASELINE.md, AUDIT_PUBLISHED.md и TECH_MAP.md. Соблюдает запреты раздела 5 мастер-плана: без полной переписи, без удаления функций и данных, без смены хранения без плана миграции.

## 0. Главный риск переезда
`localStorage` и сервис-воркер привязаны к адресу сайта. При переходе с `chyyiii.github.io` на свой домен данные пользователя **не перенесутся автоматически**, а установленная иконка «Домой» придётся поставить заново. Единственный безопасный путь переноса: файл резервной копии (экспорт на старом адресе, импорт на новом). Он уже реализован и проверен тестами, но требует отдельного, понятного пользователю сценария переезда (см. фазу C).

## Принципы
1. Приложение всё время работает; каждый шаг маленький и откатываемый (git-тег перед шагом).
2. После каждого шага: тесты, проверка вёрстки, круг «копия → восстановление» на реальных данных.
3. Сначала страховочная сетка (тесты и описания), потом разделение кода, потом сервер.
4. Offline-first сохраняется: сервер нужен для синхронизации и копий, а не для работы приложения.

## Фаза A. Страховочная сетка (FOCUS-002…004)
| Задача | Содержание | Результат |
|---|---|---|
| FOCUS-002 | Защита данных: постоянное хранилище браузера, статус, напоминание о копии | Снижен риск потери данных до переезда |
| FOCUS-003 | Обновления без «второго открытия» (сервис-воркер: сначала сеть для `index.html`) | Пользователь сразу видит новую версию |

Условие перехода к фазе B: все тесты зелёные на baseline.

## Фаза B. Реорганизация кода (без сборщика сначала)
Порядок от самого безопасного:
1. **Вынести CSS** в `css/app.css` (≈93 КБ). Логика не затрагивается.
2. **Вынести JS** одним файлом `js/app.js` (подключение `<script defer>`), обновить список кэша в `sw.js`.
3. **Выделить чистые функции** (форматирование, даты, `cleanX`, расчёты серий, лимита, прогнозов) в `js/core/*.js` с тестами на входы и выходы.
4. **Выделить слой хранения** `js/store.js` с единым интерфейсом (`load/save/remove`, режимы cloud/local). Это основа для будущего серверного режима.
5. **Выделять автономные модули** по очереди: дневник → задачи → привычки → челлендж → резервная копия → пин-код → обучение и руководство.
6. **Тяжёлые связки** (накопления, счета, регулярные платежи, журнал, плитки) разделять последними или оставить ядром.
Структура после фазы B:
```
index.html            (только разметка)
css/app.css
js/core/ js/store.js js/modules/ js/app.js
sw.js manifest.webmanifest icons/
tests/ docs/ openspec/
```
Правило шага: один модуль на ветку `focus-NNN-…`, слияние после зелёных тестов; перед каждым шагом тег `backup/…`.
Решение для Founder: сборщик (Vite) или остаёмся на подключении файлов без сборки. Рекомендация: без сборщика до фазы C, затем ES-модули и при необходимости Vite.

## Фаза C. Собственная инфраструктура
### C1. Статический хостинг на своём домене (первый шаг переезда)
- Домен + сервер (VPS) с веб-сервером (Caddy или nginx), HTTPS (Let's Encrypt), заголовки безопасности.
- Выкатка из git: сервер забирает `main` (или тег релиза) по webhook/cron; откат = переключение на предыдущий тег.
- GitHub Pages остаётся как зеркало на время переезда.
### C2. Безопасный переезд пользователей (сценарий)
1. На старом адресе выпускается версия с баннером: «Мы переехали на <новый адрес>. Сохраните копию и перенесите данные», кнопка «Сохранить копию» и ссылка.
2. На новом адресе при первом запуске предлагается «Восстановить из копии».
3. Старый адрес ещё 1–2 месяца работает как есть; данные на нём не удаляются.
4. Иконка «Домой» ставится заново (инструкция в обучении).
### C3. Серверная часть (только после C1 и фазы B)
Минимальный API для синхронизации и копий, приложение остаётся offline-first:
- Аккаунты: вход по e-mail с кодом или ключом доступа (passkey); без хранения паролей в открытом виде.
- Данные: те же документы, что в облачном режиме артефакта (`_save, _cats, _ui, _rec, _tpl, _debt, _hab` + записи), по пользователю.
- Синхронизация: версия документа + время изменения; конфликты решает «последняя запись побеждает» для настроек и слияние по `id` для записей, задач, привычек.
- Серверные копии: ежедневные, с хранением N дней, отдельно от основной базы.
- Хранилище: SQLite или PostgreSQL; бэкап базы вне сервера.
- Приватность: данные только пользователя; журналы без содержимого; план удаления аккаунта и данных.
### C4. FOCUS AI (позже)
Только поверх серверной части и по правилам раздела 10 плана: доступ к данным по разрешению, без изменений без подтверждения.
